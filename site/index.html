Coding agents shouldn't have to guess what your repository is.

DevBrain is a local MCP server that hands Claude Code, Codex, and any MCP client structured, evidence-backed facts about a repository — stack, Git state, dependencies, debt markers — and runs its build, tests, and lint only under explicit, pinned approval.

Facts, not judgment.

DevBrain is not an “AI writes code” assistant. It is the instrumentation layer underneath one: every tool does one technical thing, returns machine-readable output, and shows its evidence. What to do about that evidence stays with the agent — or with you.

Tools are capabilities

Each MCP tool performs one well-defined capability and returns validated structuredContent with an outputSchema, a short human summary, and accurate MCP annotations. An agent can branch on the result without parsing prose.

Nothing is inferred from folder names. React, Express, FastAPI, pnpm, Poetry — all of it is detected from lockfiles, manifests, and dependency metadata, with the evidence returned alongside.

Judgment is somebody else's job

devbrain_project_health will tell you a branch is fourteen commits behind upstream. It will not decide that deployment is blocked. That call belongs to a skill, a reviewer, or a person — never baked into a tool.

The same discipline applies to what DevBrain doesn't know. Unknown, unsupported, offline, and not-run are reported as themselves, never quietly rounded to “fine.”

  • UNKNOWN≠FAIL
  • NOT_RUN≠PASS
  • UNSUPPORTED≠ERROR
  • PARTIAL≠COMPLETE
  • OFFLINE≠NO_FINDINGS

Five distinctions preserved in every structured result. A vulnerability check that couldn't run is not_run, not “0 vulnerabilities.”

Ten tools. Two kinds of trust.

Five read the repository and never change it. Five execute or observe — and only what the repository itself already defines, only after you've approved it.

Repository intelligence

Non-mutating inspection. Bounded output everywhere: counts, limits, and truncated flags instead of thousands of rows in the agent's context.

  • devbrain_repo_map

    Structural map: languages, package managers, workspaces, scripts, entry points, and frameworks — each with the evidence that detected it.

    read-only
  • devbrain_project_health

    Git state, upstream divergence, hygiene observations, dependency-environment state, and red flags. Observations, not verdicts.

    read-only
  • devbrain_git_history

    Bounded commit metadata with short stats, scopable by path, author, or date. No patches.

    read-only
  • devbrain_dependency_audit

    Direct-dependency inventory plus update and vulnerability checks, with explicit degraded states when a registry or tool isn't available.

    read-only · open world
  • devbrain_find_todos

    TODO, FIXME, HACK, and XXX locations with small context, respecting Git ignore rules.

    read-only

Trusted execution & evidence

Each run is pinned to a specific, approved definition and leaves durable evidence — parsed results when the repository produces structured output, text or exit code when it doesn't, and always labeled which.

  • devbrain_run_build

    Runs the explicitly detected and approved build definition.

    executes · approved
  • devbrain_run_tests

    Runs the approved full test definition.

    executes · approved
  • devbrain_run_targeted_tests

    Runs one validated, repository-contained test target. Arbitrary extra arguments are not accepted.

    executes · approved
  • devbrain_run_lint

    Runs the approved lint definition.

    executes · approved
  • devbrain_inspect_docker

    Docker version, container status, health, ports, images, sanitized mounts, and Compose labels. No start, stop, exec, build, pull, or push — ever.

    observational

Install in three steps.

Requires Node.js 20 or newer and Git. Your repository's own package manager or Python tooling is used for execution. Docker CLI access is needed only if you call devbrain_inspect_docker.

Build the server

DevBrain is a plain TypeScript project. There's nothing to publish or sign in to.

cd devbrain-mcp
npm install
npm run build

Point your MCP client at it

Claude Code shown; any stdio MCP client works. DEVBRAIN_WORKSPACE_ROOT is the only directory DevBrain may inspect. It defaults to the process working directory.

{
  "mcpServers": {
    "devbrain": {
      "command": "node",
      "args": ["/path/to/devbrain-mcp/dist/index.js"],
      "cwd": "/path/to/your/workspace",
      "env": { "DEVBRAIN_WORKSPACE_ROOT": "/path/to/your/workspace" }
    }
  }
}

Verify it yourself

The official MCP Inspector lists every tool, its schema, and its annotations. Call one before you trust it.

npx @modelcontextprotocol/inspector node dist/index.js

Security, stated plainly.

DevBrain does not sandbox repository-controlled code. Trusted build, test, and lint definitions run with the permissions of the DevBrain process. Your approval is the security boundary; everything else is defense-in-depth.

What DevBrain enforces

A hard workspace boundary
Every path is canonicalized and must stay under DEVBRAIN_WORKSPACE_ROOT. Symlink escapes and out-of-repository test targets are rejected.
No shell, no interpolation
Every subprocess runs as an argument array with shell: false. User input is never spliced into a command string.
No arbitrary-command interface
Execution tools accept a repository path, a bounded timeout, and — for targeted tests — a repository-relative target. That's the whole input.
Capability-specific, pinned trust
Approving test does not approve build, targeted_test, or lint. Approval binds to repository identity, capability, invocation, working directory, and a SHA-256 fingerprint of the definition. Change the script and the approval no longer applies.
Clients can't approve themselves
The server can create an approval request but exposes no trust or approval tool. Trust state lives under ~/.devbrain/, outside any inspected repository.
Bounded, redacted output
Timeouts, stdout and stderr ceilings, and secret redaction on everything returned. Container environment values are never requested.

What DevBrain does not claim

It is not a sandbox
An approved definition can do anything the DevBrain process can. Command inspection blocks representative dangerous definitions; it is not isolation.
Docker access is host access
Inspection is observational, but reaching the Docker daemon may itself imply significant host privileges depending on your platform and configuration.
Full logs stay sensitive
Complete execution logs are kept on disk as local evidence and inherit your filesystem's protections. Redaction covers what is returned to the client, not the raw log.
Parsing depends on your tooling
Structured results require output the repository already produces. Otherwise DevBrain degrades to text or exit-code evidence — and says so with a confidence level.
Missing tools are reported, not guessed
An absent package manager or runtime makes a capability unsupported or leaves version provenance unknown.
Observations are point-in-time
A Docker or health result describes that moment. It is not proof of future health or isolation.
